01 / OVERVIEW

One gateway between agents and databases

Your coding client sends requests to DBMux over MCP (Model Context Protocol). DBMux checks access and SQL policy before using the server’s database connection. Database passwords remain encrypted on the gateway.

Coding client→DBMux + policy + audit→Development database

Administrators use the browser workspace to manage connections, developer tokens and history. Developers use their existing coding client and a personal MCP token; they do not need an administrator account.

02 / ADMINISTRATORS

Prepare access for your team

  1. Finish initial setup. Open the deployed DBMux URL, enter the bootstrap token supplied by the server operator, and create an administrator password of at least 14 characters. For later visits, sign in with your administrator name and password.
  2. Add a connection. Choose a stable ID such as project-dev, select Oracle or PostgreSQL, and enter the server address, port, service/database and a dedicated application account. Oracle defaults to 1521; PostgreSQL defaults to 5432.
  3. Set the scope. List explicit application schemas and choose the minimum access level needed. Keep UPDATE/DELETE WHERE safeguards enabled. Leave MCP disabled while configuring.
  4. Save and test. Use Test on the connection card. Once connectivity succeeds, enable MCP. When editing, leave the password blank to retain the stored password. Stored custom Oracle connect strings are not displayed; leave that field blank to retain the saved value.
  5. Issue personal access. In MCP access, enter a developer name, named connections, permission toggles and expiry (1–365 days). Copy the new token immediately and send it privately to its owner.
  6. Share the setup guide. In MCP installation, select the developer’s client and use Copy team setup guide. Send tokens separately from shared documentation.
The effective-access preview shows which grants survive the connection’s permissions and whether MCP is enabled. Schema restrictions and disabled tools still apply. Edit updates a token’s name, connection scope and permissions without changing its secret. Leaving expiry blank keeps the current expiry. Changes apply on the next call. Delete removes inactive tokens while preserving their activity logs. Rotate replaces a token and revokes the old one immediately. Revoke removes access without changing the database password. A lost token cannot be retrieved; issue a replacement.

03 / DEVELOPERS

Connect your coding client

  1. Ask your administrator for the MCP endpoint, your personal token, and your permitted connection IDs. You do not need database drivers or passwords.
  2. Set DB_MCP_TOKEN in the environment used by your coding client. Replace the placeholder below locally. These examples set the current shell session only; launch your client from that session. A desktop client must be able to read the same environment.
PowerShell 
$env:DB_MCP_TOKEN = "YOUR_PERSONAL_TOKEN"
macOS / Linux 
export DB_MCP_TOKEN="YOUR_PERSONAL_TOKEN"
Command Prompt 
set "DB_MCP_TOKEN=YOUR_PERSONAL_TOKEN"
  1. Save the client configuration provided by your administrator. It must reference your token environment variable and the correct endpoint. Generic MCP templates need adaptation to your client. Use HTTPS for remote access.
  2. Restart or reconnect the client. Ask your agent to list connections without making changes:
First request 
Use DBMux to call db_connections and list my available development connections. Do not make changes.

For setup details, see the official Codex, Claude Code, Cursor and VS Code instructions. Never commit tokens or paste them into team documentation.

04 / DAILY WORKFLOW

Inspect, preview, approve, review

  1. Inspect existing conventions. Start with db_connections, db_schema_context, db_describe_table and db_object_dependencies. Use explicit columns and parameter binds for queries.
  2. Capture a baseline. Use db_schema_snapshot before your feature. Keep the returned snapshot ID for comparison.
  3. Preview the proposed SQL. Use db_preview_change for each statement and read the risk and permission result. Name your migration and supply project/branch context for writes.
  4. Apply approved changes. Use db_apply_migration for ordinary CREATE/ALTER statements. High-risk changes, including DELETE with WHERE, need db_prepare_change, actual human approval, then db_execute_change with the returned changeId and confirm: true. Prepared changes expire after five minutes and are single-use.
  5. Verify and share. Capture an after snapshot, compare with db_schema_diff, and review db_change_history. Use db_export_changes for ordered successful SQL and its bind manifest; review before replay.
A starting prompt — replace PROJECT_DEV 
Using DBMux connection PROJECT_DEV, inspect the allowed schemas and relevant table dependencies. Capture a baseline schema snapshot. Propose the changes for my feature and preview each SQL statement. Include my project and branch in write context. Wait for my approval before applying changes, then capture an after snapshot and show the diff and change history.

PostgreSQL uses $1-style placeholders with bind arrays; Oracle uses :id-style placeholders with named bind objects. Queries default to 100 rows and cap at 1,000. Retained transactions use db_transaction_begin / execute / commit / rollback; they are owner-bound and roll back on expiry or server shutdown. Oracle permits DML only in retained transactions; its DDL commits implicitly.

05 / ACCESS

Understand your permissions

Level Available operations
Read Only Schema inspection and permitted SELECT queries.
Development Write Read, INSERT, UPDATE, DELETE, CREATE and ALTER, subject to policy and confirmation.
Full Development Development Write plus DROP and TRUNCATE, subject to policy and confirmation.
Custom Administrator-defined connection permission flags. Token grants still limit access.

Effective permissions are the intersection of token grants and connection grants. A broader token cannot override a restricted connection. Enabled connections, allowed schemas, blocked objects, disabled tools and token expiry are checked on every call. Arbitrary routine execution is denied.

06 / REVIEW

Read the change trail

The Dashboard shows requests and failures today, seven-day traffic, slow tools, token expiry and the last explicit connection-test results. Refreshing the dashboard does not test database connectivity. Activity logs records portal API requests, MCP requests and individual tool outcomes, including denied calls. Filter by caller, type, outcome and date range, then download all matching records as NDJSON. Search across caller names, token IDs, connection IDs, operations and request IDs, or use the exact token, connection and operation filters. View timeline links each request to its tool events and new SQL audits. SQL details load only when you select View SQL audit. Historical audits from before correlation was introduced remain available in Database history. A token name identifies the assigned owner, not a verified person at the keyboard. The source address is the direct network peer; behind a proxy it identifies that proxy. Request bodies and credentials are excluded. Activity begins after this feature is installed; earlier SQL audits remain in Database history. Pending records can indicate interrupted requests. Downloads are administrator-only and include network addresses.

In Database history, enter a connection ID and load records. Search the loaded page by project, branch, SQL or status. Expand a record to inspect SQL, parameters and context; copy details or SQL for a review. Increase Offset to load the next records (the default page contains up to 100 records).

Download all connection history exports every recorded outcome as NDJSON. Download loaded history saves the current page as JSON. Schema diffs describe catalog changes, not row changes, and cannot reconstruct exact SQL for external edits. The MCP db_export_changes tool uses successful recorded changes and includes bind manifests. Audit SQL and parameters may contain application data; share them only with authorized teammates.

A failed or pending migration may have applied some statements. Review the recorded progress and actual database state before retrying. Oracle DDL cannot be rolled back as a retained DML transaction.

07 / HELP

Get unstuck

The client reports an authentication error

Confirm DB_MCP_TOKEN is visible to the client process, then restart the client. Ask the administrator whether the token expired, was revoked or was rotated. A developer token is separate from an administrator session.

db_connections returns an empty list

Ask the administrator to check that MCP is enabled and your token includes the correct connection IDs. Creating a token does not automatically enable a connection.

A query or change is denied

Check the allowed schema, connection and token permissions, disabled tools and blocked tables/columns. UPDATE/DELETE need a top-level WHERE by default. Unknown syntax, administrative SQL, RETURNING, CASCADE and unsplit scripts are deliberately denied. A WHERE clause alone does not guarantee a safe change.

The server cannot reach the database

The administrator should use Test and check the database address, service, account, TLS and firewall. Inside Docker, localhost refers to the gateway container; use host.docker.internal for a database on the Docker host, or the appropriate reachable LAN/service address.

The copy button does not work

Use HTTPS or localhost and allow clipboard access. If access is unavailable, select the displayed text and copy manually. Command examples contain placeholders; replace those on your own machine.

08 / PRODUCT STATUS

Deployment and validation limits

DBMux is a self-hosted development gateway. Live Oracle 19c acceptance and a deployment-specific security review are still required before production use. Oracle Thin mode is implemented; Thick mode is not enabled. Client examples follow official documentation, but individual GUI clients have not been acceptance-tested.

Run one gateway process per metadata volume. Server operators must configure HTTPS, access restrictions and backups. Preserve the SQLite data and master key separately; losing the key makes encrypted data unrecoverable. Use a SQLite-aware backup or stop the gateway before copying database files.
